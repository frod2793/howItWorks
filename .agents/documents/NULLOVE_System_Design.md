# NULLOVE - 시스템 아키텍처 설계서 (System Design Document)

## 1. 아키텍처 설계 원칙 (Core Architecture Rules)

본 프로젝트는 고도화된 유지보수성, 확장성, 성능 최적화를 달성하기 위해 아래의 설계 규칙을 철저히 준수합니다.

### 1.1. SOLID & 순수 C# 로직 (Decoupling)
- **비즈니스 로직 분리**: 인게임 비즈니스 로직, 데이터 계산, 상태 관리 등은 `MonoBehaviour`를 상속받지 않는 순수 C# 클래스(POCO)로 작성합니다.
- **싱글톤 배제 (No Singleton)**: 어떠한 전역 싱글톤(Singleton) 패턴도 사용하지 않으며, 모든 객체 간의 참조는 VContainer 기반의 의존성 주입(DI)을 통해 전달합니다.
- **의존성 주입 (DIP)**: 인터페이스 정의를 통한 구체 클래스의 디커플링을 보장하며, 로직 및 뷰 컴포넌트에 인터페이스 형태로 주입합니다.

### 1.2. MVVM 패턴 기반의 UI 아키텍처
```
[사용자 입력] → View → ViewModel.Command() → Model 갱신
                                              ↓
[UI 갱신]    ← View ← ViewModel.StateChanged ←
```
- **Model**: View나 Unity 엔진에 독립적인 순수 데이터 클래스입니다. 도메인 데이터와 비즈니스 규칙만 포함합니다.
- **ViewModel**: Model 데이터를 View에 적합한 형태로 가공하여 제공하며, View가 바인딩할 상태(State)와 실행할 명령(Command)을 가지고 있습니다.
- **View**: `MonoBehaviour`를 상속하는 UI 시각화 컴포넌트입니다. 화면 갱신 및 입력 전달 기능만 수행하며, Model을 직접 참조하지 않고 오직 ViewModel을 통해서만 소통합니다.

### 1.3. 씬 전환 및 데이터 유지 (DTO)
- 씬 전환 시 유지해야 할 데이터는 전역 참조를 차단하고, `~DTO` 접미사를 가진 순수 데이터 클래스(DTO)로 캡슐화하여 씬 로더나 컨텍스트 매니저를 통해 다음 씬 초기화(Initializer) 클래스로 직접 주입합니다.

## 2. VContainer 의존성 주입 및 라이프사이클 관리

씬 내의 종속성과 글로벌 종속성은 VContainer `LifetimeScope`를 통해 다음과 같이 바인딩하고 주입합니다.

### 2.1. LifetimeScope 구성 방식
- **ProjectLifetimeScope (Global)**: 게임 시작부터 끝까지 유지될 공통 서비스(SoundService, SceneLoader, GameDataManager, LocalPersistenceService 등)를 `Lifetime.Singleton`으로 등록합니다.
- **Scene-specific LifetimeScope (Local)**: 각 씬(Title, InGame)별로 독립된 LifetimeScope를 배치하고 해당 씬 내의 뷰모델, 컨트롤러, 뷰 등을 바인딩합니다.

### 2.2. 등록 및 주입 가이드
- **순수 C# 클래스 (POCO/ViewModel/Service)**:
  `builder.Register<T>(Lifetime)` 형태로 등록하며, 인터페이스 바인딩 시 `.AsImplementedInterfaces().AsSelf()`를 체이닝합니다.
- **씬에 이미 배치된 MonoBehaviour 뷰 컴포넌트**:
  `builder.RegisterComponentInHierarchy<T>()`를 사용하여 하이어라키에서 자동으로 수집 및 주입합니다. (씬에 사전 배치 필수)
- **런타임 동적 생성이 필요한 MonoBehaviour 컴포넌트**:
  `builder.RegisterComponentOnNewGameObject<T>(Lifetime, "GameObjectName")`를 사용하여 동적 생성과 주입을 보장합니다.
- **VContainer 진입점**:
  `IStartable`, `ITickable` 등의 라이프사이클 인터페이스를 구현하는 엔트리 포인트 클래스는 `builder.RegisterEntryPoint<T>()`로 등록합니다.

## 3. 코어 시스템 설계 명세 (14개 핵심 시스템)

기획서의 14개 핵심 모듈 명세에 따른 세부 아키텍처 및 구현 명세입니다.

### 3.1. DIA (대사 시스템)
- **역할**: 대화, 나레이션, 시스템 메시지를 파싱하여 출력하고 텍스트 진행 속도, 자동 진행, 스킵 연출을 제어합니다.
- **구조**:
  - `IDialogueViewModel`을 통해 텍스트 상태 변경 이벤트를 발행합니다.
  - `DialogueView`는 텍스트 타이핑 효과(UniTask 활용) 및 UI 렌더링을 담당합니다.
  - 대사 진행(Space/Enter/LMB), 스킵(Ctrl 홀드), 자동 진행(A 토글)을 처리합니다.

### 3.2. STORY (스토리 분기 시스템)
- **역할**: 28개 씬, 13개 분기점, 9개 엔딩의 데이터베이스를 기반으로 한 조건 검사 및 씬 라우팅을 제어합니다.
- **구조**:
  - 게임의 전역 및 로컬 세션 플래그(StoryFlags)를 비교하여 다음 씬으로의 진입 조건을 판단합니다.
  - `DialogueFlowController`가 씬 진행 흐름을 제어하며 적절한 선택지를 호출합니다.

### 3.3. UI (인터페이스 시스템)
- **역할**: 본편 HUD(리소스/자원 상태), 타이틀, 설정, 세이브/로드, 도감, 인벤토리, 백로그, 일기 등의 UI 오버레이와 연출을 관리합니다.
- **구조**:
  - 각 화면별 View-ViewModel 쌍을 구성하여 VContainer에 바인딩합니다.
  - 뒤로가기(Esc) 동작에 대한 우선순위 기반 팝업 닫기 가드 로직을 구현합니다.

### 3.4. SAVE (세이브/로드 시스템)
- **역할**: 단일 세이브 슬롯 관리(수동/자동 덮어쓰기) 및 다회차 통계와 해금 상태를 저장하는 글로벌 진행도 저장을 분리 처리합니다.
- **구조**:
  - `SaveDataDTO`: 카토 재고, 5축 감정 상태, 감시도, 신뢰도, 회차 인식도, 현재 씬 및 줄 번호, 분기 이력, 인벤토리 아이템을 포함합니다.
  - `GlobalProgressDTO`: 다회차 정보(누적 플레이 타임, 해금 엔딩 수, 도감 등록 수, 서브플롯 진행도)를 별도 유지합니다.

### 3.5. EMO (감정 및 자원 시스템)
- **역할**: 5축 감정 수치(슬픔, 기쁨, 호기심, 공포, 혼란) 변동 처리 및 그리움 합성 로직, 3종 자원(카토 재고, 감시, 신뢰도), 회차 인식도(0~5) 상태를 관리합니다.
- **구조**:
  - `EmotionModel`에서 슬픔 >= 3 이고 기쁨 >= 3일 때 '그리움' 상태를 활성화합니다.
  - 방사형 레이더 차트 갱신을 위해 데이터가 바뀔 때마다 변경 이벤트를 발행하여 `SidePanelView`에 실시간으로 투영합니다.

### 3.6. CONF (대면 시스템)
- **역할**: 씬 13~16의 클라이맥스 전투를 대체하는 대면 선택지 카드 4개 메뉴 구성 및 해금 조건 처리를 제어합니다.
- **구조**:
  - 4메뉴(1: 대화하다, 2: 기억하다, 3: 느끼다, 4: 놓아주다) 중 특정 엔딩 달성 여부 및 자원 조건(예: 그리움 활성)을 판단하여 카드 잠금 상태를 동적으로 제어합니다.

### 3.7. INV (인벤토리 시스템)
- **역할**: 단서, 쪽지, 열쇠 등 획득한 아이템을 수집하고 UI에 표출하며, 분기 및 진엔딩 영향 표시를 관리합니다.
- **구조**:
  - 아이템은 고유 ID와 함께 영향도 유형(일반 단서, 분기 영향-다이아몬드, 진엔딩-별) 정보가 DTO에 포함되어 View에 바인딩됩니다.

### 3.8. SND (사운드 시스템)
- **역할**: 3레이어 BGM(베이스/멜로디/환경음) 볼륨을 독립적으로 제어하며, 현재 감정과 회차 상태에 따라 사운드 레이어를 런타임에 동적으로 온/오프시킵니다.
- **구조**:
  - `SoundService`는 오디오 믹서(AudioMixer) 그룹을 사용해 베이스, 멜로디, 환경음 볼륨을 부드럽게 페이드(DOTween 활용) 처리합니다.

### 3.9. SET (설정 시스템)
- **역할**: 볼륨(마스터/BGM/SFX/보이스), 윈도우 비활성 시 음소거 토글, 화면 해상도 및 입력 변경 설정을 저장하고 즉각 반영합니다.
- **구조**:
  - 설정 상태 데이터는 로컬 디스크에 암호화 저장되며, 게임 부팅 및 런타임 변경 시 오디오/그래픽 모듈에 즉시 투영됩니다.

### 3.10. LOG (백로그 시스템)
- **역할**: 텍스트 출력 히스토리를 스크롤 뷰로 조회하고, 각 라인의 음성 파일을 재생하며, 특정 대사 시점으로 씬 상태를 강제 롤백합니다.
- **구조**:
  - `BacklogDTO`에 누적 대사 정보 및 해당 대사 시점의 자원 스냅샷을 보존하여, 되감기 시점 롤백 시 상태를 복구할 수 있는 DTO 패턴을 채택합니다.

### 3.11. LOOP (회차 시스템)
- **역할**: 글로벌 진행도 및 회차 인식도 수치에 맞춰 런타임에 씬의 스크립트 텍스트, 캐릭터 일러스트 상태, 막간 챕터 등을 변형합니다.
- **구조**:
  - `StoryModel`에서 회차 인식도(0~5) 변수를 기반으로 분기 매트릭스를 연동하여 동적으로 대사 번역 키 또는 씬 데이터를 로드합니다.

### 3.12. DIARY (일기 시스템)
- **역할**: 각 씬이 끝날 때마다 상태 변화와 독백을 자동 기록하며, 현재 회차에 맞춰 색조가 시프트되는 다이어리 UI를 갱신합니다.
- **구조**:
  - 씬 클리어 시점에 DTO 형태로 일기 내용 및 감정 5축 상태를 수집하여 세이브 데이터에 영구 보존합니다.

### 3.13. INTERLUDE (막간 시스템)
- **역할**: 챕터 사이에서 진행되는 4개의 메타 성격의 인터루드 연출을 활성화하고 제어합니다.
- **구조**:
  - 씬 로더와 스토리 모델이 협업하여 특정 챕터 클리어 후 메인 씬 대신 메타 인터루드 씬을 로드하고 진행하도록 설계합니다.

### 3.14. TIME (시간대 시스템)
- **역할**: 씬의 구성에 맞게 아침, 낮, 밤 시간대에 따라 배경 이미지 필터링(색조 시프트)을 수행하고 시간대 한정 이벤트 발생을 판별합니다.
- **구조**:
  - `TimeOfDay` 값에 따라 UI와 배경 스프라이트의 쉐이더 파라미터 혹은 컬러 틴트를 동적으로 변경(DOTween)합니다.

## 4. 코딩 표준 및 코드 안전성 가이드 (Coding & Safety Standards)

본 프로젝트의 안정적인 빌드와 클린 코드 작성을 위해 다음 규칙을 반드시 적용합니다.

- **변수 및 필드 네이밍**:
  - `private` 필드는 `m_` 접두사 + camelCase를 적용합니다. (예: `m_catoStock`)
  - `public` 프로퍼티와 메서드는 PascalCase를 적용합니다. (예: `CurrentCatoStock`)
  - 인터페이스는 `I` 접두사를 적용합니다. (예: `ISoundService`)
  - UI 버튼 OnClick 이벤트 등에 Inspector를 통해 직접 할당하는 public 콜백 메서드는 `func_` 접두사를 붙입니다. (예: `public void func_OnNewGameButtonClick()`)
- **중괄호 `{ }` 생략 금지**:
  - 모든 `if`, `else if`, `else`, `for`, `while` 구문에는 내용이 단 한 줄이더라도 반드시 중괄호를 생략하지 않고 Allman Style로 작성합니다.
- **루프 최적화**:
  - GC 할당 오버헤드를 막기 위해, 컬렉션이나 배열을 순회할 때는 `foreach` 대신 반드시 **`for` 루프**를 채택합니다.
- **유니티 Safety**:
  - `UnityEngine.Object`를 상속받는 객체에 대해서는 널 조건부 연산자(`?.`, `??`)의 사용을 엄격히 금지합니다. 유니티 엔진의 Fake Null 이슈로 인해, 널 체크는 반드시 `if (obj != null)` 형태로 명시하여 작성합니다.
- **주석 및 리전 작성 금지 (HowItWorks 프로젝트 엄격 규칙)**:
  - 기존 코드의 주석이나 `#region` 블록은 그대로 유지하되, **새로 작성하는 코드에는 어떠한 신규 주석(XML, 일반 주석) 및 신규 `#region` 블록도 추가하지 않습니다.** 코드는 오직 직관적인 네이밍과 구조적인 분리로 스스로를 설명하도록 작성해야 합니다. (이 규칙은 다른 일반 문서화 규칙에 대해 최우선으로 적용됩니다.)
