# 제품 스펙 관리 가이드

제품 스펙은 무엇을 만들지와 어떤 결과를 수용할지를 정의합니다. 구현 기술을 선결정하지 않으며 파일명은 `YYYY-MM-DD-기능명-spec.md` 형식을 사용합니다.

## 언제 작성하는가

- 새로운 게임 기능 또는 사용자 흐름을 합의할 때
- 기존 기능의 동작·품질 목표를 크게 변경할 때
- 기획·아트·클라이언트·서버 사이의 수용 기준이 필요할 때

## 프로필 기반 작성 계약

1. `.agents/config/project-profile.conf`를 참조하되 제품 요구를 특정 기술 이름으로 고정하지 않습니다.
2. 영향 범위는 `${source_root}`, 검증 범위는 `${test_root}`로 표현합니다.
3. 기술 제약이 필요하면 `선택 프로필의 역할`과 사용자 가치의 관계를 설명합니다.
4. `dependency_injection=none`도 지원하므로 컨테이너 존재를 제품 전제로 삼지 않습니다.
5. 성능 기능은 `적용 상태`, 재현 가능한 `측정 근거`, 허용 한계를 넘을 때의 `롤백 조건`으로 정의합니다.
6. Open Questions는 실제 미결정 사항이 있을 때만 남기고 결정되면 제거합니다.

`test_root`가 없는 프로젝트는 임의 폴더 대신 프로젝트가 제공하는 대체 수용 검증을 기록합니다.

## 작성 프로세스

1. [_TEMPLATE.md](_TEMPLATE.md)를 복사합니다.
2. 사용자 문제, 유저 스토리, 측정 가능한 수용 기준을 작성합니다.
3. 프로필과 충돌하는 요구가 있다면 제약이 아니라 미결정 사항으로 분리합니다.
4. 성능 목표의 측정 환경과 롤백 기준을 합의합니다.
5. 승인된 스펙을 바탕으로 [설계 문서](../design-docs/)를 작성합니다.

```text
제품 스펙(What) → 설계 문서(How) → 실행 계획(Verified Steps)
```
