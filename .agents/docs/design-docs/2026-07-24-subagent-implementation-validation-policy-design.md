# 서브 에이전트 구현·검증 실행 정책 설계

**상태**: 사용자 방향 승인, 문서 검토 대기  
**작성일**: 2026-07-24  
**적용 대상**: 범용 Unity 하네스와 Unity 클라이언트 업무용 하네스

## 1. 목표

두 하네스의 구현 실행 정책을 다음 세 원칙으로 통일한다.

1. 컴파일 오류 확인을 제외한 검증·테스트는 사용자가 현재 요청한 경우에만 실행한다.
2. 모든 구현 파일 생성·수정은 서브 에이전트가 수행한다.
3. 서브 에이전트의 구현 완료 후 메인 에이전트가 독립적으로 코드를 리뷰한다.

이 정책은 테스트·CI·QA의 품질 기준을 제거하지 않는다. 사용자가 실행을 요청하지 않은 검증은 `not_run`으로 남기고, 검증 완료나 CI 통과를 주장하지 않으며 관련 상태를 전환하지 않는 실행 권한 경계다.

## 2. 역할 분리

### 메인 에이전트

- 프로젝트의 `.agents/AGENTS.md`, 프로필, 아키텍처와 사용자 요구를 먼저 읽는다.
- 실제 파일과 현재 상태를 분석하고 구현 범위와 계획을 사용자에게 제시한다.
- 사용자 승인 후 구현 규칙 묶음을 작성해 서브 에이전트에게 전달한다.
- 구현 파일을 직접 생성하거나 수정하지 않는다.
- 서브 에이전트 완료 보고 후 요구사항 일치와 코드 품질을 독립적으로 리뷰한다.
- 중요한 리뷰 지적이 있으면 같은 서브 에이전트에게 수정 범위를 전달하고 다시 리뷰한다.
- 실행한 컴파일 확인, 사용자 요청으로 실행한 검증·테스트와 `not_run` 항목을 구분해 최종 보고한다.

### 구현 서브 에이전트

- 전달받은 사용자 요구, 승인 범위와 프로젝트 하네스 규칙을 구현 전에 읽는다.
- 전달받지 않은 외부 작업, 리팩터링, 테스트와 검증으로 범위를 넓히지 않는다.
- 최소 변경으로 구현하고 관련 없는 사용자 변경을 보존한다.
- 코드 또는 스크립트 변경에는 해당 환경의 컴파일·구문 오류 확인까지만 기본 수행한다.
- 사용자가 현재 요청하지 않은 린트, Unit·Integration·EditMode·PlayMode 테스트, 런타임 검증, 수동 시각 검증과 빌드는 실행하지 않는다.
- 완료 보고에 변경 파일, 구현 내용, 컴파일 결과, 미실행 검증과 남은 위험을 기록한다.

## 3. 서브 에이전트 전달 계약

메인 에이전트는 구현 요청마다 다음 내용을 빠짐없이 전달한다.

| 필수 항목 | 내용 |
|---|---|
| 사용자 요구 | 현재 요청의 원문과 목표 |
| 승인 범위 | 승인된 계획과 변경 가능한 기능 |
| 최우선 규칙 | 프로젝트 `.agents/AGENTS.md` 및 연결된 필수 문서 |
| 구현 규칙 | 아키텍처, 코딩·명명 규칙, Karpathy Guidelines |
| 대상 파일 | 생성·수정 가능한 정확한 경로 |
| 금지 범위 | 서드파티, 관련 없는 변경, 외부 서비스와 승인되지 않은 작업 |
| 테스트 권한 | 현재 요청에서 허용된 검증·테스트 목록 또는 `none` |
| 컴파일 확인 | Unity Editor·MCP·프로젝트 명령 등 실제 오류 확인 방법 |
| 완료 보고 | 변경 파일, 구현 요약, 컴파일 결과, `not_run`, 우려 사항 |

규칙 묶음이 누락되거나 충돌하면 서브 에이전트는 구현을 추측해 진행하지 않고 메인 에이전트에 필요한 정보를 요청한다.

## 4. 실행 권한 매트릭스

| 작업 | 기본 실행 | 조건 |
|---|---|---|
| 코드·스크립트 컴파일 또는 구문 오류 확인 | 필수 | 변경 언어와 프로젝트에 실제 확인 진입점이 있을 때 |
| 정적 코드 리뷰 | 필수 | 서브 에이전트 구현 완료 후 메인 에이전트가 수행 |
| 하네스 린트·정적 정책 검사 | 금지 | 사용자가 현재 요청한 경우에만 실행 |
| Unit·Integration 테스트 | 금지 | 사용자가 현재 요청한 범위만 실행 |
| Unity EditMode·PlayMode 테스트 | 금지 | 사용자가 현재 요청한 범위만 실행 |
| 런타임·씬·Inspector·시각 검증 | 금지 | 사용자가 현재 요청한 범위만 실행 |
| Player Build·외부 Unity CI | 금지 | 사용자가 현재 명시적으로 요청한 경우에만 실행 |
| Jira·Slack·GitHub·이메일·Connector 작업 | 금지 | 기존 외부 작업 권한 정책과 동일하게 현재 명시적 요청 필요 |

문서만 변경되어 컴파일 대상이 없으면 컴파일 확인을 `N/A`로 기록한다. 컴파일 진입점을 사용할 수 없거나 오류 확인이 막히면 정확한 원인을 보고하고 컴파일 성공으로 처리하지 않는다.

## 5. 구현과 리뷰 흐름

```text
실제 파일·규칙 분석
-> 설계·구현 계획
-> 사용자 승인
-> 메인 에이전트가 규칙 묶음과 범위를 서브 에이전트에 전달
-> 서브 에이전트 구현
-> 컴파일·구문 오류 확인
-> 서브 에이전트 완료 보고
-> 메인 에이전트 정적 코드 리뷰
-> 중요 지적이 있으면 같은 서브 에이전트가 수정
-> 메인 에이전트 재리뷰
-> 테스트 미실행 경계를 포함한 최종 보고
```

코드 리뷰는 구현 결과가 사용자 요구와 승인 범위를 충족하는지 먼저 확인하고, 이어서 결함, 회귀 위험, 아키텍처, 수명주기, 직렬화, 비동기, 보안과 유지보수성을 확인한다. 메인 에이전트의 리뷰는 Unit·Integration·런타임 테스트를 대신하지 않는다.

## 6. 기존 CI·업무 게이트와의 관계

- 범용 하네스의 테스트·마일스톤 정책은 실행 가능한 검증 규격으로 유지한다.
- 업무용 하네스의 AI 리뷰 70점, Compile·Unit·Integration·Build Validation과 QA 완료 조건도 유지한다.
- 사용자가 검증·테스트를 요청하지 않으면 구현과 메인 에이전트 코드 리뷰까지만 수행한다.
- 미실행 결과는 `not_run`으로 기록하고 `ci_tests_passed`, `ci_passed`, Approve, Merge 또는 Done으로 자동 전환하지 않는다.
- 사용자가 이후 검증을 요청하면 요청된 범위만 실행하고 기존 증거 계약에 따라 상태를 전환한다.

## 8. 현재 변경의 검증 경계

이번 정책 구현에서는 사용자의 별도 검증·테스트 요청이 없으므로 하네스 린트와 테스트 스위트를 실행하지 않는다. 서브 에이전트가 문서와 계약 기대값을 수정한 뒤 메인 에이전트가 정적 코드 리뷰로 다음을 확인한다.

- 두 하네스의 최상위 규칙이 같은 실행 권한 경계를 갖는가
- 온보딩·검증 정책·실행계획·업무 SOP에 반대 지시가 남아 있지 않은가
- 서브 에이전트 전달 계약과 구현 후 리뷰 절차가 명시됐는가
- 기존 CI·QA 품질 게이트가 삭제되거나 통과로 오인되지 않는가
- 실행하지 않은 검증이 `not_run`으로 보고되도록 안내하는가

자동 검증 결과는 사용자가 별도로 요청할 때만 생성한다.
